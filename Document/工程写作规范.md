# Agent 工程写作规范

仅供执行工程写作任务的 Agent 阅读。

本规范源于对范本《GTCRN-Light 底模（v1）——网络设计思路与工程手记》（`GTCRN-C-Streaming-Micro/Document/v1/GTCRN-Light底模网络解析.md`）写作特点的系统提炼。凡是要求"按照这个范式写文章"的任务，Agent 均须按本规范组织写作。

---

## 1. 术语与适用范围

### 1.1 工程手记

本规范所称**工程手记**，指对某一技术对象（网络结构、算法模块、系统架构、移植与优化方案、疑难机制）所做的"设计思路解析"式深度技术文章：按信号流/数据流顺序逐层拆解，每个设计选择都回答"为什么"，全部数字可追溯实测来源，代价与局限照实坦白。

### 1.2 适用任务

- 神经网络/模块/算法的设计思路解析。
- 架构演进、流式化、量化、裁剪等工程改造手记。
- 疑难机制、关键公式或实现细节的原理拆解。
- 与传统方法的对照与取舍分析。

### 1.3 核心读者

具备工程基础、但不一定熟悉该领域每个前置概念的同行工程师。文章必须自包含：读者不需要读源码、不需要会话历史即可读懂。

---

## 2. 文章骨架（强制结构）

按以下骨架组织全文：

1. **写在前头**：文章定位；该对象在整个演进链（版本链）中的位置；一句话概括设计目标；实测声明——写明文中所有数字经何物核对（checkpoint/源码/实测运行），不是抄配置。
2. **正文 1..N 章**：沿信号流/数据流顺序编号分章，每章对应一个处理阶段或一个设计主题。每章内部"先说为什么这么做，再说具体怎么做"。
3. **关键设计决策回顾**：把散落在正文里的"为什么"集中收拢；每个决策是一个真实的岔路口，写清"当初换一个选择会是什么局面"，以及哪些约束动不得、哪些动一发牵全身。
4. **实现备忘**：部署、移植、复现时的坑（死代码、参数口径、固定矩阵、BN 折叠、小常数、非因果点等），每条都是踩过或可能踩的。
5. **局限**：坦率列出该版本的短板，并标注它们在后续演进中由哪个版本/方案解决；短板就是后续工作的理由。
6. **结尾**：一句话收尾 + 数据实测核对声明（核对自哪个文件）。

---

## 3. 叙事原则

### 3.1 问题驱动

每节开头提出一个根本问题（"降噪网络的输出到底是什么东西？""为什么不选更常见的 Mel？""为什么拆成三个通道？"），整节内容就是对这个问题的回答。

必须遵守：

1. 每章/每小节至少回答一个明确的"为什么"；禁止平铺罗列"有什么"而不说"为什么长这样"。
2. 标题可以是问题本身，也可以是结论短语；但节内第一段必须把问题摆出来。
3. 问题要有递进感：先回答根本问题（输出是什么），再回答手段问题（怎么用尽量少的参数做到）。

### 3.2 为什么先于怎么做

任何结构细节之前先讲动机、约束与矛盾。

必须遵守：

1. 引入一个模块前，先交代它要解决什么矛盾（如"细节越精细越好 vs 算力硬约束"）。
2. 每个设计选择都要给理由；理由必须是工程性的（算力、参数、可训练性、可流式性、梯度健康），禁止"业界常用"式空洞理由。

### 3.3 层层递进推导

从一个朴素起点出发，暴露其天花板，再引出下一步改进。

必须遵守：

1. 形成"起点 → 局限性 → 升级"的推导链：实数增益 → 相位天花板 → 复数掩码。
2. 每一步升级都要交代代价与收益（见 6.1）。
3. 升级必须是必然的（上一步确实解决不了），禁止为了炫技引入无关概念。

### 3.4 伏笔与回调

全文是一张交叉引用网。

必须遵守：

1. 前文埋伏笔："见第 N 节""这是第 N 节要坦白的局限之一""这个决定为 v3 留了活路"。
2. 后文兑现回调："第 N 节预告过的代价""再强调一次第 N 节埋的伏笔"。
3. 交叉引用必须真实存在，禁止虚指。

### 3.5 演进视角

设计决策要放进演进链里讲。

必须遵守：

1. 随时标注该设计对后续演进（流式化、量化、裁剪、移植）的影响：哪些部件流式友好、哪些不友好、哪些是"立项时就规划好的"。
2. 解释决策时要有时间纵深："与其到时候推倒重训，不如从底模就把这个自由度锁死"。

### 3.6 前因后果：每个理论的五步叙事

每个理论（公式、定理、算法、变换）都按"前因后果"五步展开，缺一不可：

1. **问题从哪来**：先讲清"需要解决什么问题"——这个理论出现之前，工程上遇到了什么麻烦（哪些现象解释不了、哪些计算做不动、哪些方法失效）。
2. **引入理论**：给出理论本身——必要的公式保留并配"其中"式符号说明，讲清物理/几何/工程含义。
3. **能解决什么**：理论建立后解决了哪些问题、能处理什么样的信号与场景。
4. **性质与限制**：着重讲清理论的性质（适用条件、假设前提）与限制（什么情况下失效、边界在哪）——这是本范式的重点，推导过程点到为止。
5. **好处与优势**：相比其他可用方法，这套解决思路好在哪、付出了什么代价。

必须遵守：

1. 五步顺序不许颠倒；"限制"一步不许省略或一笔带过。
2. 限制必须是具体的（假设条件、适用域、失效模式、代价），禁止"也有一定局限性"式空话。
3. 每章可按"一个理论 = 一节"编排；理论之间有依赖时按依赖顺序排列，并用前一步的限制引出下一个理论（前因后果接力）。

### 3.7 深入浅出：性质与限制优先，推导适度

写给学生与工程师都能读懂的"深"文章。

必须遵守：

1. 保留必要的公式并逐一说明符号，但**不展开冗长推导链**：一步到位的替换、冗长积分/级数演算可引用结论并给出直观解释，把篇幅留给性质、限制与工程含义。
2. 每个公式出现后，立即回答"它说明什么性质、在什么条件下成立、什么时候不成立"。
3. 直观解释优先：先给直觉（类比、几何图像、数值例子），再给公式；禁止公式连排无解释。
4. "深入"体现在性质与限制讲透，"浅出"体现在每一步都有直觉抓手；禁止用推导堆砌冒充深度。

## 4. 表达手法

### 4.1 直觉先行，类比辅助

用类比把机制讲透，但类比之后必须跟上严谨内容。

必须遵守：

1. 类比要贴切且单义：音量旋钮、眼镜、直通车、快递、筛子、编辑部。
2. 类比只作引子，禁止替代论证；类比之后必须跟公式、形状、参数量等严谨内容。
3. 同一篇文章的类比体系要自洽，不混用互斥的比喻。

### 4.2 人话翻译

术语之后给"翻译成人话"的一句话解读。

必须遵守：

1. "Mel 告诉你音阶走了多少级，ERB 告诉你尺子刻度有多粗"式的一句话翻译。
2. 允许克制的人称化语气（"说实话""讽刺的是""这是后话"），但结论必须严谨；禁止轻浮语气稀释技术密度。

### 4.3 一句话总结

关键节点用加粗的一句话收束（"ERB 是模糊，SFE 是锐化""既调音量又转相位"）。

必须遵守：

1. 每章末尾尽量有一句话总结，概括该章在全局中的角色。
2. 总结句要可引用、可对照，禁止空泛。

### 4.4 加粗与强调

全文用加粗标记关键结论，让扫读也能抓住主干。

必须遵守：

1. 每段最多一两个加粗点；加粗的是结论，不是所有术语。
2. 关键结论（代价、天花板、分野）优先加粗。

## 5. 实证要求

### 5.1 数字必须实测

所有参数量、张量形状、计算量、训练后权重数值、评价指标必须实测核对，禁止抄配置文件或凭印象估计。

必须遵守：

1. 正文写明核对来源（哪个 checkpoint、哪段代码、哪次运行）。
2. 区分"可训练参数"与"固定矩阵/死代码占位"：总数要能对账（如 173,301 个数值 vs 139,482 个可训练参数）。
3. 算力盘点要落到"每帧乘加数 × 帧率 = 每秒吞吐"的预算口径。

### 5.2 公式配符号说明

每个公式后跟"其中 X 为……"式符号逐一说明。

必须遵守：

1. 禁止出现未解释的符号；首次出现的符号就地定义。
2. 公式与文字衔接：公式前一句交代"为什么需要这个公式"，公式后解释"它说明什么"。

### 5.3 表格归纳

能用表格的用表格。

必须遵守：

1. 参数/形状变化用表格逐阶段列出（阶段、形状、频率维）。
2. 方案对比用表格（标准卷积 vs DW+PW：参数、每次输出乘加、总乘加）。
3. 设计决策用表格（做什么、怎么干、对应模块）。
4. 表格前后要有文字引导，禁止表格孤悬无解释。

### 5.4 图片与图注

重要机制必须配图，每张图有图注说明"看什么、得出什么结论"。

必须遵守：

1. 图片服务具体结论：数据流图、前后对比图、真实数据演示图、感受野/参数分布图。
2. 图注（斜体）写清：图是什么、关键看点在哪、支持哪条结论。
3. 正文必须引用图片编号并解释；禁止只插图不解释。
4. 图片由工作目录内的脚本生成（见 8.2），禁止装饰性图片、临时截图冒充正式图。

## 6. 工程立场

### 6.1 代价与收益并陈

每个设计选择都写明代价，哪怕很小。

必须遵守：

1. "代价几乎可以忽略"也要明说代价是什么（如输出通道 1→2）。
2. 折中的代价要写清换来了什么（如 ERB 损失高频掩码分辨率，换来频率维缩小 57%）。

### 6.2 局限与瑕疵坦白

死代码、未调用层、命名误导、非因果点照实记录。

必须遵守：

1. 发现死代码/未使用参数必须点名（哪个类、多少参数、state_dict 里在不在），并说明对后续工作（裁剪、加载器）的影响。
2. 专设"局限"章：每条局限标注后续由哪个版本/方案解决；解决不了的写明原因。
3. 禁止把局限写得无关紧要；禁止只说成功面。

### 6.3 预算与经济学语言

算参数账、算力账，用预算语言解释取舍。

必须遵守：

1. 关键模块写明参数占比、算力占比，并解释"钱花在哪、为什么花在这"。
2. 用"该花的钱一分不省，能省的钱一分不多花""经济学拉满"式语言把取舍讲透；压缩的最终回报要在下游兑现（贵的模块跑在最小维度上）。

### 6.4 对照传统方法

把新方案与传统/基线方法并排对照。

必须遵守：

1. 说明新方法与传统方法的本质分野（端到端回归 vs 统计模型两步走）。
2. 说明多花的代价买到了什么能力（非平稳噪声、低 SNR、冷启动）；两者不是替代关系时照实说明。

## 7. 自包含性：前置概念插播

遇到读者可能陌生的概念，就地讲清，保证文章自包含。

必须遵守：

1. 用引用块/前置概念小节（"前置概念①：……"）就地讲解（DWConv+PWConv、BatchNorm、ERB 等）。
2. 前置概念要讲"是什么、怎么算、为什么存在"，并落到本对象的实例数字上。
3. 前置概念的位置贴近首次使用处；不打断主线时用引用块，需要多步时独立小节。

---

## 8. 交付物与文件规范

### 8.1 文章

- 自包含 Markdown；公式用 LaTeX（块级 `$$ … $$` 或行内 `$…$`）；中文书写。
- 图片用相对路径插入；文末有实测核对声明。

### 8.2 图片与脚本

- 图片统一编号 Fig01 起三位数字递增，文件名含简洁中文描述（如 `Fig01_实数增益与复数掩码.png`）。
- 所有正式图片必须由工作目录内的 Python 脚本生成（推荐 matplotlib），脚本留档、注明运行命令；图片可复现、可重生成。
- 内容更新保留原编号，语义完全改变才分配新编号；废弃编号不复用。
- 流程图必须生成图片，禁止 Mermaid/PlantUML/ASCII 字符图冒充正式交付物。
- 画图纪律（碰撞检测）：按"无识图能力"的最坏假设画图。图元一律先规划坐标再落笔：节点框之间、框与文本之间预留充足间距；连线走线避开节点框与文本，多边交叉改用弧线或正交绕行；图例放空白区不压曲线；坐标轴范围预留 5–10% 余量。禁止文本溢出框（穿箱）、连线穿越图元、多线拧成一团的布局。
- 中文字体：图中的中文须显式配置可用中文字体（如 SimHei / Microsoft YaHei），禁止缺字方框。
- 生成后复核：每张图生成后尽力复核——模型支持图像输入时用 read_image 读回逐张检查，否则写脚本检测 artist 边界框相交；发现穿箱、重叠、乱线即修正脚本重画，禁止把布局混乱的图写入文档。

### 8.3 产出目录

文章、图片、脚本集中放在用户指定的产出目录内；未指定时与用户确认，禁止散落到仓库各处。

图片目录通用约定（用户已指定）：所有图片一律放在**当前产出目录（当前文章文档所在目录）下的 `figures/` 子目录**，编号沿用 Fig01 起三位递增；正文用相对路径引用；绘图脚本与图片同目录或在其 `scripts/` 子目录留档。目录随每次任务的实际产出目录而定，禁止在规范或文档中写死绝对路径。

## 9. 写作流程

1. **材料核实**：读源码、配置、checkpoint，实测所有要写进文章的数值；记录核对来源。禁止边写边编数字。
2. **规划章节**：按信号流/数据流列大纲；每章标注要回答的问题与要配的图。
3. **生成图片**：先写脚本生成全部图片（先规划坐标布局、做碰撞避让），检查每张图的结论成立且布局无重叠，再动笔正文。
4. **分章撰写**：按第 2、3、4 章原则写正文；边写边维护伏笔/回调清单。
5. **决策回顾与备忘**：收拢"为什么"，补实现备忘。
6. **局限与收尾**：坦率列短板与演进对应关系，写实测声明。
7. **全文自检**：按第 11 节逐项自检。

---

## 10. 禁止事项（违反即失败）

- 禁止写入未实测核对过的数字、张量形状、计算量或指标；禁止抄配置文件数字冒充实测。
- 禁止公式出现未解释的符号；禁止平铺罗列结构而不回答"为什么"。
- 禁止只讲收益不讲代价；禁止隐瞒死代码、瑕疵与局限；禁止把局限写得无关紧要。
- 禁止类比替代论证；禁止"如图""显然"式无结论图片与图注缺失。
- 禁止图片由临时截图冒充脚本生成的正式图；禁止无编号、无图注、无正文引用的图片。
- 禁止交叉引用虚指（引用不存在的章节/图）。
- 禁止把文章写成 API 文档式清单或论文式抽象堆砌——必须是"先讲为什么、再讲怎么做"的工程手记。
- 禁止省略"限制"环节或把限制写成一句空话；禁止用冗长推导链堆砌冒充深度。
- 禁止把存在穿箱、重叠、乱线的图片写入文档。

---

## 11. 完成前自检（全部通过才可标记完成）

- 骨架：写在前头、正文分章、关键设计决策回顾、实现备忘、局限、实测声明齐全？
- 叙事：每节回答了明确的"为什么"？推导链"起点→局限→升级"完整？伏笔与回调都能兑现？
- 实证：所有数字有实测来源？公式符号全部有说明？表格有引导？每张图有图注、正文引用、对应脚本？
- 立场：每个设计选择都写了代价？死代码与局限坦白？参数/算力账清楚？与传统方法有对照？
- 自包含：读者不需要源码与对话历史即可读懂？前置概念就地讲清？
- 交付：图片编号连续、脚本留档、文件在指定产出目录内？
- 理论：每个理论的五步前因后果齐全？性质与限制讲透而推导适度？
- 图形：图片无穿箱/重叠/乱线？中文无缺字？布局经复核？

## 12. 项目专章：统计信号处理基础书稿

对《统计信号处理基础——估计与检测理论》讲解项目，在通用规范之上追加以下约定（源自 `Document\统计信号处理\需求说明.md`）：

1. 分章交付：每个章节写成一个独立文档，放在 `Document\统计信号处理\Documents\` 下。
2. 临时文件：清单、列表等临时文件放在 `Document\统计信号处理\Temp\` 下。
3. 章节编排：按 3.6 前因后果五步编排每个理论；按 3.7 深入浅出（性质与限制优先、推导适度）。
4. 图片：放在当前章节文档所在目录的 `figures/` 子目录（见 8.3 图片目录通用约定），Fig01 起编号，遵守 8.2 的碰撞检测纪律。
5. 终检：全部文章写完后做一次严格终检——文章是否满足前因后果/性质与限制/深入浅出要求；图片是否满足目录/编号/无碰撞要求；是否存在事实错误；是否按规范分段。
