# Agent 项目研究规范

仅供参与 `Document/Update/Research/` 下独立研究项目的 Agent 阅读。

本规范参考 `Document/Agent开发规范.md`，但面向算法分析、方案调研、仿真验证、实物模型演示与研究文档编写，不采用 Version 四阶段、Stage 或 SubStage 工作方式。

---

## 1. 术语与适用范围

### 1.1 研究项目目录

`Document/Update/Research/` 下承载某一项独立研究任务的直接子目录，称为该任务的**研究项目目录**，也称**工作目录**。

例如：

```text
Document/Update/Research/可活动骨架的分析/
Document/Update/Research/3D Force Filed Rebuild/
```

Agent 在哪个研究项目目录内接受和执行任务，哪个目录就是本次工作的唯一工作目录。目录名称和研究内容不固定。

`Document/Update/Research/` 本身是研究项目的容器目录，不应被当作某个具体研究任务的工作目录；本规范文件除外。

### 1.2 当前根目录

本规范中的**当前根目录**指仓库根目录。Agent 可以只读访问根目录及工作目录之外的代码、文档、模型、数据和配置，以获取研究背景或参考实现，但不得对其进行任何修改。

### 1.3 适用任务

本规范适用于但不限于：

- 算法原理分析与技术路线研究。
- 数值仿真、可视化和对比实验。
- 实物或 3D 模型上的算法演示。
- 原型代码、数据处理脚本和实验工具编写。
- 研究报告、说明文档和需求解读。

---

## 2. 核心原则

### 2.1 工作目录强隔离

研究任务的所有写入必须限制在当前研究项目目录内，不得穿透该目录影响仓库中的其他目录、代码或文档。

必须遵守：

1. 所有新建或修改的代码、文档、图片、模型、数据、日志、配置、缓存和实验结果，都保存在工作目录内。
2. 不得修改工作目录之外的任何既有文件，包括仓库根目录、主工程源码、其他研究项目和公共文档。
3. 不得为了让研究原型接入主工程而直接修改主工程。需要说明接入方案时，只在工作目录内编写接口说明、补丁示例或独立原型。
4. 不得把临时脚本、生成结果或中间文件写入仓库根目录、系统默认输出目录或其他项目目录。
5. 工具必须指定输出路径时，应显式将输出路径设置到工作目录内；如工具不可避免会修改工作目录外内容，应停止执行并记录为不能自决问题。
6. 可以读取和复制工作目录外的参考材料，但复制品必须放入工作目录，并注明来源；不得反向覆盖原文件。
7. 引用外部代码、模型或数据时，应记录来源路径、用途以及是否产生了本地副本。

目录边界判断原则：

> 如果一次操作会导致工作目录外的文件内容、文件名、目录结构、版本状态或生成物发生变化，则该操作禁止执行。

### 2.2 零上下文研究交付

研究文档和实验产物应让一个没有对话历史的新 Agent 或审阅者，仅通过工作目录中的内容即可理解：

- 研究背景、目标与范围。
- 需求如何变化，当前方向如何形成。
- 使用了哪些输入、算法、参数和假设。
- 如何复现实验与生成图片。
- 结果说明了什么，存在哪些限制。
- 哪些问题由用户决定，哪些问题由 Agent 自决。

禁止使用“按之前讨论”“和上次一样”等依赖对话历史的表述。

### 2.3 无阶段工作

研究项目不划分阶段，不创建 Stage、SubStage，也不设置阶段门禁。Agent 按当前已确认需求持续推进研究，并维护问题清单、历史主线和研究产物。

无阶段不等于无约束：新的正式需求文档必须先完成解读和问题清单审阅流程；不能自决问题未关闭前，不得开展依赖该决策的实质工作。

### 2.4 证据优先

算法结论应尽可能由公式、数据、代码、图像、模型或可复现实验支持。不能仅凭文字推断宣称算法有效，也不能把未经验证的预期写成实验结论。

## 3. 工作目录与推荐结构

每个研究项目目录应逐步形成以下结构；仅在实际需要时创建可选目录：

```text
研究项目目录/
├── 历史主线.md                 # 必须保留，持续更新
├── 当前研究文档.md             # 名称按项目内容确定
├── 问题清单.md                 # 新需求审阅期间的活动清单
├── figures/                    # 图片较多时创建
│   ├── Fig001_名称.png
│   ├── Fig002_名称.png
│   └── ...
├── archived/                   # 必须保留，用于归档需求和已回复清单
│   ├── REQ_YYYYMMDD_需求名称.md
│   ├── QL_YYYYMMDD_需求名称_已回复.md
│   └── ...
├── scripts/                    # 可选：仿真、绘图、数据处理代码
├── models/                     # 可选：实物或 3D 模型
├── data/                       # 可选：输入数据与处理后数据
└── outputs/                    # 可选：非文章图片类实验输出
```

目录结构可按项目规模简化，但必须满足：

- `历史主线.md` 始终位于工作目录根部。
- `archived/` 始终位于工作目录内。
- 大量图片统一进入 `figures/`。
- 所有产物不得离开工作目录。

## 4. 历史主线

### 4.1 基本要求

每个研究项目必须在工作目录根部保留一份 `历史主线.md`，用于记录需求演变和大的方向性调整。它是项目演进的主索引，不替代研究正文、问题清单或实验报告。

以下事件必须记录：

- 收到新的需求或正式需求文档。
- 用户补充、删除或修改需求。
- 研究目标、核心假设或技术路线发生明显调整。
- 仿真对象、实物模型、评价指标或关键数据源发生变化。
- 用户对不能自决问题作出决定。
- Agent 的重要自决对研究方向产生实质影响。
- 关键实验推翻原假设，导致后续方向改变。

### 4.2 记录格式

按时间顺序追加，保留旧记录，不覆盖历史：

```markdown
## H003 - YYYY-MM-DD - 调整标题

- 触发来源：用户需求 / 需求文档 / 问题清单回复 / 实验结果
- 原方向：...
- 新方向：...
- 调整原因：...
- 影响范围：文档、算法、脚本、模型、图片或数据
- 关联文件：相对工作目录的路径
- 决策性质：用户决定 / Agent 自决
- 当前状态：生效 / 待确认 / 已撤销
```

编号采用 `H001`、`H002`、`H003` 递增，不因内容撤销而复用。仅修正错别字、排版等不改变需求含义的操作，无需单独记录。

## 5. 新需求文档处理与问题清单

### 5.1 触发条件

当用户提供一份新的、较正式的需求文档，或要求 Agent 读取工作目录中的新需求文件时，必须执行本节流程。零散且含义明确的简单指令可以直接记入 `历史主线.md`；若其中存在路线分歧，仍应生成问题清单。

### 5.2 需求解读

Agent 应先完整阅读需求文档，并识别：

- 明确目标与交付物。
- 研究边界和禁止事项。
- 输入数据、模型、算法与工具约束。
- 图片、仿真、实物演示和对比要求。
- 验证方法与成功标准。
- 与当前研究方向的新增、修改、冲突和废止关系。
- 隐含假设、信息缺口和潜在风险。

### 5.3 问题分区

Agent 必须在工作目录根部生成或更新 `问题清单.md`，明确区分以下两类问题，交由用户审阅：

#### 不能自决问题

满足任一条件即归入该区：

- 涉及研究目标、技术路线或交付形式的重大分歧。
- 选错后会造成大量返工，或使研究结论失去意义。
- 需求之间相互冲突，无法依据现有材料消解。
- 缺少只有用户能够提供的数据、模型、评价标准或偏好。
- 操作可能突破工作目录边界或修改仓库其他内容。
- 涉及无法由 Agent 接受的安全、授权或真实性风险。

不能自决问题未得到用户回复前，Agent 不得执行依赖该答案的工作，但可以继续进行与该问题无关的阅读、整理和验证。

#### 可以自决问题

不存在重大路线分歧、可依据资料和工程常识稳妥处理的问题归入该区。Agent 必须给出自决方案、理由、风险和置信度，用户可在审阅时修改。

可以自决问题不阻塞工作；除非用户明确否决，Agent 按记录方案执行。

### 5.4 每条问题的内容

每条问题至少包含：

1. 问题描述。
2. 对研究结果的影响。
3. 推荐方案或自决方案。
4. 必要时提供 1 至 2 个备选方案及差异。
5. 风险预警。
6. 置信度。
7. 需要用户如何回复，或 Agent 将如何自决。

推荐格式：

```markdown
# 问题清单 - 需求名称 - YYYY-MM-DD

## 不能自决问题

### Q001 - 问题标题
- 问题描述：...
- 影响：...
- 推荐方案：...
- 备选方案：...
- 风险预警：...
- 置信度：70%
- 请用户回复：同意推荐方案 / 选择备选方案 / 补充信息
- 用户回复：

## 可以自决问题

### Q002 - 问题标题
- 问题描述：...
- 自决方案：...
- 自决理由：...
- 风险预警：...
- 置信度：95%
- 用户修订：
```

不允许提交无建议的裸问题，也不允许把多个独立问题合并为一条。

### 5.5 用户审阅与归档

1. Agent 将 `问题清单.md` 提交用户审阅。
2. 用户可以直接在文档的“用户回复”或“用户修订”位置填写答复。
3. Agent 读取回复后，检查是否产生新的不能自决问题；如有，应在当前清单中追加并再次提交审阅。
4. 所有不能自决问题关闭后，将相关决定写入 `历史主线.md`。
5. 将已回复的问题清单移动到 `archived/`，命名为 `QL_YYYYMMDD_需求名称_已回复.md`。
6. 工作目录根部不长期保留已关闭清单；下一份新需求到来时重新创建 `问题清单.md`。

## 6. 需求文档归档

### 6.1 归档原则

新的正式需求文档在完成阅读和解读后，应保存在工作目录的 `archived/` 中。归档的目的，是保存当时收到的需求依据并避免临时文件散落。

### 6.2 归档时机

- 若原需求文档已经位于工作目录内：完成解读并生成问题清单后，将其移动到 `archived/`。
- 若原需求文档位于工作目录之外：只读访问原文件，在 `archived/` 中保存副本或转写后的 Markdown 版本，不得移动、重命名或修改原文件。
- 若需求直接来自对话且内容足够正式：可整理成一份归档文档，注明“来源：用户对话整理”，不得补写用户未表达的要求。

### 6.3 命名规则

统一采用：

```text
REQ_YYYYMMDD_简明需求名称.扩展名
```

如同一天存在同名文件，追加两位序号：

```text
REQ_YYYYMMDD_简明需求名称_02.md
```

归档文件应保留原始含义。若为了统一格式进行转写，应在文件开头注明原文件名、原路径、归档日期和转写说明。

## 7. 算法、仿真与可视化

### 7.1 主动生成图像

编写算法原理、算法效果或仿真说明文档时，Agent 应主动判断哪些内容仅靠文字难以表达，并优先通过图像进行说明，而不是等待用户逐张提出要求。

优先考虑生成：

- 算法流程图、数据流图或几何关系图。
- 输入、处理中间态与输出的并列对比图。
- 参数变化、误差分布、收敛曲线或敏感性曲线。
- 二维热力图、矢量图、等值线、切片图或三维场分布图。
- 实物模型或 3D 模型上的算法前后效果。
- 基线方法、目标方法与真实值之间的对比。
- 失败案例、边界案例和局限性示意图。

图片必须服务于具体结论，不为增加数量而生成装饰性图片。

### 7.2 实物与 3D 模型演示优先

当用户要求用实物或 3D 模型演示算法时，应优先把算法应用到具有实际形状、结构或表面的模型上，而不是仅使用抽象点云、随机曲面或纯数学图形。

例如，在 3D 力场重建研究中，应倾向于：

1. 选取或构造可辨识的实物 3D 模型。
2. 在模型表面或周围定义输入采样、载荷或观测数据。
3. 执行重建算法并映射结果。
4. 生成真实值、输入状态、重建结果和误差分布的图片。
5. 在文章中并列展示并解释差异。

若无法获得适用模型、数据或渲染能力，应在问题清单或研究文档中写明限制，不得用抽象示例冒充实物验证。

### 7.3 仿真可复现性

仿真工作至少保留：

- 可执行脚本或源代码。
- 输入数据或明确的数据生成方式。
- 关键参数、随机种子和运行环境说明。
- 运行命令和输出路径。
- 图像生成代码或明确的生成步骤。
- 评价指标、对比基线和结果解释。

研究文档中的图片应能追溯到对应脚本、输入和参数。若图片经过人工后处理，应说明处理内容。

### 7.4 结论边界

- 仿真结果只能证明当前模型、参数和数据条件下的表现。
- 合成数据结果不得表述为真实设备或真实场景验证。
- 单个案例不得直接推广为普遍结论。
- 图像应同时展示有利结果和关键失败案例，避免选择性呈现。

### 7.5 流程图必须生成图片

当生成的研究文档需要使用流程图时，Agent 应优先编写 Python 脚本生成一张具体的流程图图片，并将该图片插入文档，不得直接使用 Mermaid、PlantUML、Markdown 字符图、ASCII 图或其他仅由文档渲染器临时绘制的流程图作为正式交付物。

必须遵守：

1. 流程图生成脚本保存在工作目录内，推荐放入 `scripts/`。
2. 流程图图片按第 8 节规则保存到 `figures/`，使用 `Fig001`、`Fig002` 等统一编号。
3. 文档使用相对路径插入图片，并在正文中引用图片编号、说明流程起点、关键判断和输出结果。
4. 生成图片时应保证节点文字、连线、箭头、判断分支和颜色图例清晰可读。
5. 流程发生变化时，应同步修改 Python 生成脚本并重新生成图片，避免只手工修改最终图片。
6. 推荐使用 Python 的 `matplotlib`、`Pillow`、`networkx`、`graphviz` 等能力；所用依赖和运行命令应记录在研究文档或脚本说明中。
7. 如果当前环境确实无法安装或调用所需绘图库，应先尝试使用现有 Python 图形能力完成；仍无法生成时，将原因记录为问题，不得擅自改用文档内直接绘制的流程图冒充最终图片。

## 8. 图片管理与文章引用

### 8.1 创建 figures 目录的条件

满足任一条件时，应在工作目录下创建 `figures/`：

- 文章预计生成 5 张及以上图片。
- 图片由多个脚本或多轮实验生成。
- 图片存在多个版本、对比组或子图。
- 图片需要被多份文档复用。

图片较少时也可以使用 `figures/`；一旦创建，文章所用图片应统一存放其中，避免散落在工作目录根部。

### 8.2 图片编号与命名

每张独立图片使用稳定、唯一、递增的编号：

```text
Fig001_输入模型.png
Fig002_采样点分布.png
Fig003_算法重建结果.png
Fig004_重建误差分布.png
```

要求：

- 编号采用三位数字，从 `Fig001` 开始递增。
- 文件名包含简洁、可辨识的中文或英文描述。
- 图片内容更新时保留原编号；图片语义完全改变时分配新编号。
- 已删除或废弃的编号不复用，避免历史文档引用错位。
- 多子图可使用 `Fig005a`、`Fig005b`，合并后的总图使用 `Fig005`。

### 8.3 文档引用

文章必须使用相对路径插入图片，并在正文中明确引用编号：

```markdown
如图 Fig003 所示，重建结果保留了主要受力区域。

![Fig003 算法重建结果](figures/Fig003_算法重建结果.png)

*图 Fig003：算法重建结果。参数：采样间距 5 mm，正则化系数 0.01。*
```

每张图应有图题；关键实验图还应注明输入条件、核心参数或对比对象。不得只插图而不在正文解释图片支持的结论。

### 8.4 图片质量

- 坐标轴、单位、图例、颜色条和关键标记应完整可读。
- 对比图尽量统一视角、尺度、色域和分辨率。
- 颜色映射应避免误导；误差图和场分布图应标明数值范围。
- 三维图应选择能够清楚展示差异的视角，必要时提供多个视角或切片。
- 图片生成失败或质量不足时，应修正后再写入文章，不得把临时截图当作正式证据。

## 9. 研究文档标准

算法或研究说明文档应根据任务需要包含以下内容：

1. 背景与目标。
2. 研究范围与不研究范围。
3. 输入、输出及数据来源。
4. 关键假设与限制。
5. 算法原理、公式、流程与参数。
6. 实验或仿真设计。
7. 实物或 3D 模型说明。
8. 图像、结果与对比分析。
9. 失败案例和风险。
10. 可复现步骤。
11. 结论及后续建议。
12. 关联的历史主线、归档需求和问题清单路径。

所有关键结论应能对应到数据、图片、代码或引用资料。引用仓库外或工作目录外内容时，应使用只读来源路径或公开来源说明，不得暗示其由本研究项目生成。

---

## 10. 自检与完成标准

Agent 在提交研究成果前至少检查：

### 10.1 目录边界

- 是否所有修改和生成物都位于当前研究项目目录内？
- 是否意外修改了仓库根目录、主工程或其他研究项目？
- 是否有工具把缓存、日志或输出写到了工作目录外？

### 10.2 需求与决策

- 新需求是否已解读并归档？
- 是否生成了不能自决和可以自决问题清单？
- 用户回复后的清单是否已归档？
- 需求变化和方向调整是否写入 `历史主线.md`？

### 10.3 算法与证据

- 算法说明是否有足够的图像或实物演示？
- 仿真是否可复现，脚本、输入、参数和命令是否齐全？
- 图片是否真的支持正文结论？
- 是否明确区分合成仿真、模型演示和真实实验？
- 文档中的流程图是否由工作目录内的 Python 脚本生成，并作为编号图片插入？

### 10.4 图片与文档

- 大量图片是否集中在 `figures/`？
- 每张图片是否有唯一编号、清晰命名和图题？
- 文档是否使用相对路径，链接是否有效？
- 是否包含失败案例、限制和风险，而非只展示理想结果？

仅当以上检查通过，且不存在未关闭的、会影响结论的不能自决问题时，方可将当前研究成果标记为完成。

## 11. 禁止事项

- 禁止修改研究项目目录之外的任何文件。
- 禁止把研究代码直接写入主工程或其他子项目。
- 禁止创建 Stage、SubStage 或沿用 Version 四阶段目录。
- 禁止跳过正式需求文档的问题清单审阅流程。
- 禁止在用户未回复不能自决问题时擅自选择重大技术路线。
- 禁止在问题清单关闭后不归档，或删除用户回复记录。
- 禁止只写算法效果描述而不提供可验证证据。
- 禁止用抽象随机数据冒充实物模型或真实场景验证。
- 禁止使用 Mermaid、PlantUML、Markdown 字符图或 ASCII 图代替应由 Python 生成并插入的正式流程图图片。
- 禁止生成大量未编号、无图题、无正文解释的图片。
- 禁止覆盖历史主线中的旧记录或复用已使用的历史编号、图片编号。
